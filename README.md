# Предиктор задержек наземного транспорта — MVP

Прогнозирует, опоздает ли машина больше чем на 3 минуты через 10–15 минут, и показывает риск на диспетчерском дашборде.

**Статус:** расписание реальное (data.mos.ru), фактическое движение пока смоделировано. Весь конвейер готов к подмене источника на телематику организаторов.

## Как устроено

```
GPS-отметки (NDTP) ──► data_sources/gps_telemetry.py ──┐
                                                          │  events: StopEvent (domain/schema.py)
плановое расписание ──► data_sources/mos_ru_schedule.py ─┤
(data.mos.ru)                                            ▼
                                            engine/stream_state.py (потоковый расчет признаков)
                                                          │
                              ┌───────────────────────────┼──────────────────────┐
                              ▼                           ▼                      ▼
                     model/training.py          service/risk_service.py    replay_build.py
                     (обучение CatBoost)        service/replay_service.py  (кэш записанного дня)
                                                           │
                                                    app/api.py (FastAPI)
                                                           │  JSON: кадры, KPI, тревоги
                                                           ▼
                                                  web/ — дашборд на React
```

Признаки считает один и тот же класс `StreamState` и при обучении, и в живом сервисе, поэтому модель в проде видит ровно то, на чем училась.

### Слои пакета `app/`

Код разложен по ответственности, а не свален в один файл на функцию — это должно позволять менять один слой, не трогая остальные:

| Слой | Файлы | Что делает | От чего изолирует |
|---|---|---|---|
| `domain/` | `schema.py` | Канонические структуры: `StopEvent`, `ScheduleTables`, `DayContext`, `RiskPrediction` | Формат конкретного источника данных |
| `data_sources/` | `base.py`, `mos_ru_schedule.py`, `gps_telemetry.py`, `processed_repository.py` | Адаптеры сырых данных к канонической схеме + единая точка чтения/записи parquet | Конкретные названия колонок data.mos.ru/NDTP, формат хранения на диске |
| `simulation/` | `synthetic_telemetry.py` | **Временная заглушка.** Синтетический «факт» в той же схеме, что и реальная телематика | Отсутствие реальных данных на время MVP |
| `engine/` | `feature_definitions.py`, `stream_state.py` | 20 признаков и потоковое состояние (`StreamState`) | ML-библиотеку и источник событий |
| `model/` | `predictor.py`, `evaluation.py`, `artifacts.py`, `training.py` | Обёртка над CatBoost, метрики, загрузка артефактов, обучение | Остальной код от конкретной ML-библиотеки |
| `service/` | `risk_service.py`, `replay_service.py` | Бизнес-логика дашборда: приём событий и текущий риск; кадры записанного дня, KPI, тревоги | HTTP/FastAPI от бизнес-логики |
| — | `api.py` | Тонкий FastAPI-слой поверх `service/` | — |
| — | `replay_build.py` | Прогон тестового дня → серверный кэш для `replay_service` | — |
| `web/` | React + TypeScript + Vite | Отрисовка того, что посчитал API | Фронтенд от предметной логики |

**Почему так:** если завтра поменяется формат входных данных (другие колонки, другой источник телематики, другой город), меняется один файл в `data_sources/` — `engine`, `model`, `service` и дашборд по-прежнему работают, потому что все они говорят на одном языке (`domain/schema.py`), а не завязаны на конкретные имена колонок.

## Дашборд

`web/` — приложение на React + TypeScript (Vite). Главный принцип: **вся предметная логика на сервере**. Фронтенд не распаковывает данные, не интерполирует положение машин, не знает порогов риска и не считает KPI — он запрашивает готовый кадр и рисует его.

| | Где считается |
|---|---|
| Положение машин между остановками | `service/replay_service.py` |
| Уровень риска (низкий/средний/высокий) | `config.py: RISK_LEVELS` → API |
| KPI, список тревог, «медленные» перегоны | `service/replay_service.py` |
| Подписи признаков, проценты в панели модели | `api.py: /api/model` |
| Проекция карты, зум, панорама, анимация ползунка | фронтенд (это отрисовка) |

### API

| Эндпоинт | Что отдает |
|---|---|
| `GET /api/replay/day` | метаданные записанного дня + геометрия сети (запрашивается один раз) |
| `GET /api/replay/frame?t=&mode=&min_level=&trip=` | кадр на момент `t`: машины, KPI, тревоги, медленные перегоны, карточка выбранного рейса |
| `GET /api/replay/timeline?mode=` | шкала времени: сколько машин с высоким риском в каждый момент дня |
| `GET /api/live/snapshot` | то же по форме, но из живого потока событий |
| `GET /api/model` | качество модели из `reports/metrics.json` |
| `POST /api/events` | пачка событий «машина прошла остановку» |
| `POST /api/context` | погода/праздник на сегодня |
| `GET /api/health` | что доступно сервису прямо сейчас |

Кадр приходит колонками (`vehicles.lon[]`, `vehicles.level[]`, …), а не списком объектов, и сжимается gzip — на пиковых часах это десятки килобайт. Один кадр считается за доли миллисекунды: события всех рейсов лежат в плоских numpy-массивах, отсортированных по `рейс × KEY_SPAN + время`, поэтому положение всех машин находится одним `searchsorted`, без цикла по рейсам.

Если данных еще нет, API отвечает `503` с подсказкой, какую команду запустить, и подхватывает данные без перезапуска.

Панель «Качество модели» строится из `reports/metrics.json` — переобучили модель, дашборд обновился сам.

## Запуск

### В Docker

Требования: Docker Engine с Compose v2. На Windows — Docker Desktop с Linux-контейнерами.

1. Положите данные организаторов в `data/hackathon/` с исходной структурой каталогов
   (`train/`, `test/`, `validate/`, `labels/`). Эти данные подключаются к контейнерам
   `ml` и `player` только для чтения и в образ не копируются.
2. Если используется Яндекс.Карта, скопируйте `.env.example` в `.env` и задайте ключ:

   ```dotenv
   VITE_YANDEX_MAPS_API_KEY=ваш_ключ
   NDTP_PLAN_TZ_OFFSET_S=0
   ```

   `.env` находится в `.gitignore`; ключ нельзя коммитить. Vite получает его через
   Docker build-arg и вшивает во frontend во время сборки.
3. Из корня репозитория запустите весь стек:

   ```bash
   docker compose up --build
   ```

После успешного старта:

- дашборд: http://localhost:8000;
- Swagger: http://localhost:8000/docs;
- проверка готовности: http://localhost:8000/api/health;
- вход NDTP для внешнего эмулятора: `host.docker.internal:9201`;
- внутренний backend: `backend:8000`, внутренний ML-сервис: `ml:8100`.

Сервисы Compose:

| Сервис | Назначение | Команда / порт |
|---|---|---|
| `ml` | CatBoost-инференс по телеметрии | `uvicorn ml_service.server:app`, внутренний `8100` |
| `backend` | FastAPI и TCP-приёмник NDTP | внутренний `8000`, опубликован `9201:9201` |
| `web` | nginx + собранный `web/dist` | опубликован `8000:80` |
| `player` | воспроизведение `traffic.csv` в NDTP с ускорением ×10 | поток с 06:00 длительностью 1080 минут |

Режим «Симуляция» работает сразу из файлов `data/processed/replay.pkl` и таблиц
расписания, которые входят в репозиторий и Python-образ. Примерно через минуту после
старта `player` накапливается 10 минут виртуальной телеметрии и появляются live-прогнозы.
По окончании потока машины исчезают с карты через 120 секунд. Перезапуск потока:

```bash
docker compose restart player
```

Остановить стек и удалить только созданные контейнеры/сеть:

```bash
docker compose down
```

Чтобы запустить интерфейс и API без встроенного проигрывателя:

```bash
docker compose up --build ml backend web
```

### Локально без Docker

```bash
pip install -r requirements.txt
./run_all.sh                          # ~15 минут: данные -> обучение -> кэш дня -> сборка фронтенда
uvicorn app.api:app                   # API + дашборд на http://localhost:8000
```

Разработка фронтенда — с горячей перезагрузкой, запросы к API идут через прокси Vite:

```bash
uvicorn app.api:app --reload          # терминал 1
cd web && npm run dev                 # терминал 2, http://localhost:5173
```

## Результаты (синтетика, отложенная неделя)

Главная метрика — машины, которые **сейчас идут по графику**, но опоздают через 10–15 минут. Именно их диспетчер не видит без прогноза.

| | PR-AUC | Точность тревог при полноте 70% |
|---|---|---|
| CatBoost | 0.87 | 83% |
| Правило «смотреть на текущее опоздание» | 0.66 | 56% |

Эти цифры доказывают, что конвейер работает и модель использует сигналы сверх текущего опоздания. Точность на реальных данных будет другой: модель выучила правила симулятора.

## Когда придут данные организаторов

1. Написать `decode_ndtp()` в `app/data_sources/gps_telemetry.py` под их формат.
2. Если в телематике нет номера рейса — сопоставить машину с рейсом по наряду или по «маршрут + направление + ближайший плановый рейс».
3. Убрать `app.simulation.synthetic_telemetry` из `run_all.sh`, положить реальные события в `data/processed/fact/` через `processed_repository.save_fact_day()` (или слать их напрямую в `POST /events`).
4. Заменить погоду из симулятора на реальную (Open-Meteo), праздники — на производственный календарь (`app/config.py:HOLIDAYS`).
5. Если поменяется формат самого расписания (другой город, GTFS) — реализовать новый класс по образцу `MosRuScheduleSource` (протокол `ScheduleSource` в `app/data_sources/base.py`), остальной код не трогать.
6. Перезапустить `python -m app.model.training` и `python -m app.replay_build`.

## Ограничения MVP

- Сервис хранит состояние в памяти одного процесса (`service/risk_service.py`); для прода нужен Redis или аналог.
- Записанный день целиком держится в памяти процесса API (`service/replay_service.py`) — это демонстрационный режим; в проде работает Live (`/api/live/snapshot`).
- Геометрия маршрутов — прямые между остановками (в наборах data.mos.ru нет трасс).
- CORS в `app/api.py` открыт на все источники ради удобства демо — для прода сузить `allow_origins`.
