# Предиктор задержек наземного транспорта — MVP

Прогнозирует, опоздает ли машина больше чем на 3 минуты через 10–15 минут, и показывает риск на диспетчерском дашборде.

**Статус:** расписание реальное (data.mos.ru), фактическое движение пока смоделировано. Весь конвейер готов к подмене источника на телематику организаторов.

## Как устроено

```
GPS-отметки (NDTP) ──► data_sources/gps_telemetry.py ──┐
                                                          │  events: StopEvent (domain/schema.py)
плановое расписание ──► data_sources/mos_ru_schedule.py ─┤
(data.mos.ru)                                            ▼
                                            engine/stream_state.py (потоковый расчет признаков)
                                                          │
                              ┌───────────────────────────┼──────────────────────┐
                              ▼                           ▼                      ▼
                     model/training.py          service/risk_service.py   dashboard_export.py
                     (обучение CatBoost)         + app/api.py (FastAPI)    (data.json для демо)
```

Признаки считает один и тот же класс `StreamState` и при обучении, и в живом сервисе, поэтому модель в проде видит ровно то, на чем училась.

### Слои пакета `app/`

Код разложен по ответственности, а не свален в один файл на функцию — это должно позволять менять один слой, не трогая остальные:

| Слой | Файлы | Что делает | От чего изолирует |
|---|---|---|---|
| `domain/` | `schema.py` | Канонические структуры: `StopEvent`, `ScheduleTables`, `DayContext`, `RiskPrediction` | Формат конкретного источника данных |
| `data_sources/` | `base.py`, `mos_ru_schedule.py`, `gps_telemetry.py`, `processed_repository.py` | Адаптеры сырых данных к канонической схеме + единая точка чтения/записи parquet | Конкретные названия колонок data.mos.ru/NDTP, формат хранения на диске |
| `simulation/` | `synthetic_telemetry.py` | **Временная заглушка.** Синтетический «факт» в той же схеме, что и реальная телематика | Отсутствие реальных данных на время MVP |
| `engine/` | `feature_definitions.py`, `stream_state.py` | 20 признаков и потоковое состояние (`StreamState`) | ML-библиотеку и источник событий |
| `model/` | `predictor.py`, `evaluation.py`, `artifacts.py`, `training.py` | Обёртка над CatBoost, метрики, загрузка артефактов, обучение | Остальной код от конкретной ML-библиотеки |
| `service/` | `risk_service.py` | Бизнес-логика живого сервиса: приём событий, текущий риск | HTTP/FastAPI от бизнес-логики |
| — | `api.py` | Тонкий FastAPI-слой поверх `RiskService` | — |
| — | `dashboard_export.py` | Прогон тестового дня → `dashboard/data.json` | — |

**Почему так:** если завтра поменяется формат входных данных (другие колонки, другой источник телематики, другой город), меняется один файл в `data_sources/` — `engine`, `model`, `service` и дашборд по-прежнему работают, потому что все они говорят на одном языке (`domain/schema.py`), а не завязаны на конкретные имена колонок.

## Дашборд

`dashboard/index.html` — статичный HTML-файл, который **не содержит данных внутри себя**. Он загружает данные одним из двух способов, переключается прямо в интерфейсе:

- **Демо-день** — `fetch("./data.json")`, сгенерированный `python -m app.dashboard_export`. Полная анимация дня: карта, воспроизведение, шкала времени.
- **Live** — опрашивает `GET /risk` работающего сервиса (`app/api.py`) каждые 4 секунды и показывает реальный текущий риск. Адрес API вводится в интерфейсе и запоминается в браузере.

При запуске `uvicorn app.api:app` дашборд также отдаётся статикой на `/dashboard/` — сервис и фронтенд можно поднять одной командой.

Панель «Качество модели» строится из `reports/metrics.json` (важность признаков, точность по уровням риска), а не зашита в HTML — переобучили модель, дашборд обновился вместе с `data.json`.

## Запуск

```bash
pip install -r requirements.txt
./run_all.sh                          # ~15 минут: данные -> обучение -> data.json
uvicorn app.api:app --reload          # сервис + дашборд на /dashboard/
```

Демо-день без сервиса: просто откройте `dashboard/index.html` в браузере (или раздайте `dashboard/` любым статик-сервером — `file://` не даёт `fetch` работать в части браузеров).

## Результаты (синтетика, отложенная неделя)

Главная метрика — машины, которые **сейчас идут по графику**, но опоздают через 10–15 минут. Именно их диспетчер не видит без прогноза.

| | PR-AUC | Точность тревог при полноте 70% |
|---|---|---|
| CatBoost | 0.87 | 83% |
| Правило «смотреть на текущее опоздание» | 0.66 | 56% |

Эти цифры доказывают, что конвейер работает и модель использует сигналы сверх текущего опоздания. Точность на реальных данных будет другой: модель выучила правила симулятора.

## Когда придут данные организаторов

1. Написать `decode_ndtp()` в `app/data_sources/gps_telemetry.py` под их формат.
2. Если в телематике нет номера рейса — сопоставить машину с рейсом по наряду или по «маршрут + направление + ближайший плановый рейс».
3. Убрать `app.simulation.synthetic_telemetry` из `run_all.sh`, положить реальные события в `data/processed/fact/` через `processed_repository.save_fact_day()` (или слать их напрямую в `POST /events`).
4. Заменить погоду из симулятора на реальную (Open-Meteo), праздники — на производственный календарь (`app/config.py:HOLIDAYS`).
5. Если поменяется формат самого расписания (другой город, GTFS) — реализовать новый класс по образцу `MosRuScheduleSource` (протокол `ScheduleSource` в `app/data_sources/base.py`), остальной код не трогать.
6. Перезапустить `python -m app.model.training` и `python -m app.dashboard_export`.

## Ограничения MVP

- Сервис хранит состояние в памяти одного процесса (`service/risk_service.py`); для прода нужен Redis или аналог.
- Демо-режим дашборда — воспроизведение записанного дня; в проде используется Live-режим (`GET /risk`).
- Геометрия маршрутов — прямые между остановками (в наборах data.mos.ru нет трасс).
- CORS в `app/api.py` открыт на все источники ради удобства демо — для прода сузить `allow_origins`.
