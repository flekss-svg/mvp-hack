# Предиктор задержек наземного транспорта

Система заранее предупреждает диспетчера: **эта машина сейчас идет по графику, но через 10–15 минут опоздает**. Она принимает телематику по NDTP, сопоставляет отметки с расписанием, считает признаки, прогнозирует отклонение от графика и показывает на дашборде карту, риск по машинам, тревоги и причины прогноза.

Три модуля:

| Модуль | Где | Что делает |
|---|---|---|
| ML-ядро | `ml_service/` | Признаки, модели CatBoost (регрессор отклонения и классификатор early / ontime / late), причины прогноза, оценка текущего отставания, прогноз по потоку |
| Backend | `app/` | FastAPI, приемник NDTP по TCP, записанный день, контракт API |
| BI-дашборд | `web/` | React + TypeScript: карта, уровни риска, тревоги, карточка ТС |

## Запуск

### Данные

Данные в репозиторий не входят. Перед запуском положите их в `data/`:

```
data/
├── hackathon/          раздача организаторов: train/, test/, validate/, labels/, sample_submission.csv
│                       (нужна для прогноза по NDTP и для файла сдачи)
├── processed/          расписание и готовый записанный день для режима «Симуляция» (уже в репозитории)
└── raw/                расписание data.mos.ru, наборы 60661, 60662, 60664, 60665, 60666
                        (нужно, только чтобы пересобрать «Симуляцию» с нуля)
```

Без `data/hackathon/` сервис поднимется, но в `/api/health` будет `forecast.ready: false` (в `error` — какого файла не хватает), а режим Live покажет машины без прогнозов. «Симуляция» работает сразу: ее данные лежат в `data/processed/`.

### Ключ карт

Подложка карты — Яндекс.Карты. Ключ JavaScript API (developer.tech.yandex.ru) вшивается в дашборд при сборке, поэтому его нужно указать до сборки:

```bash
cp .env.example .env              # для Docker: ключ в VITE_YANDEX_MAPS_API_KEY
cp web/.env.example web/.env      # без Docker (npm run build / npm run dev): то же в web/.env
```

Оба `.env` не коммитятся. Без ключа все работает, но вместо подложки карты будет подсказка о ключе.

### В Docker

```bash
cp .env.example .env              # ключ Яндекс.Карт, см. выше
docker compose up --build
```

| Сервис | Что делает | Порт |
|---|---|---|
| `web` | дашборд (nginx); `/api/`, `/docs`, `/openapi.json` проксирует в `backend` | **8000** → http://localhost:8000 |
| `backend` | API + прием NDTP (один worker) | **9201** — сюда шлет эмулятор (`host.docker.internal:9201`) |
| `ml` | ML-ядро: прогноз по потоку NDTP на моделях хакатона | внутренний 8100 |
| `player` | проигрывает поток NDTP из `data/hackathon/validate/`: с 06:00, 18 часов данных, ×10 | — |
| `emulator` | по желанию: эмулятор терминалов организаторов, 5 машин без расписания шлют NDTP в `backend` | — |

Эмулятор организаторов включается профилем — его образ берется из их архива, в git его нет:

```bash
docker load -i data/hackathon/ndtp-telemetry-emulator.tar
docker compose --profile emulator up -d
```

Он шлет случайное блуждание и текущее время: это машины без расписания, на карте они серые и без прогноза. Реальный день организаторов проигрывает `player`.

Данные организаторов положите в `data/hackathon/`: в образ они не попадают, `ml` и `player` получают их томом только для чтения. Расписание и записанный день для «Симуляции» уже в репозитории и едут в образ.

Что должно быть после запуска:
- http://localhost:8000 открывается, режим «Симуляция» работает сразу;
- `curl http://localhost:8000/api/health` — у `replay`, `live`, `ndtp`, `forecast` везде `ready: true`, у `forecast` — `mode: service`;
- режим Live: машины появляются через несколько секунд, прогнозы — примерно через минуту (10 минут потока при ×10);
- Swagger: http://localhost:8000/docs.

Поток закончился (~1,8 часа) — машины исчезнут с карты через 2 минуты. Проиграть заново: `docker compose restart player`.

Проверить весь стек автоматически (соберет, проверит и остановит): `./scripts/docker-smoke.sh`.

**На сервере.** Все, что нужно сервису, лежит в git, кроме двух вещей — их переносят руками:
1. `data/hackathon/` (данные организаторов, в git не хранятся). После копирования обязательно
   `chmod -R a+rX data/hackathon`: в контейнере сервисы работают от отдельного пользователя, и без
   прав на чтение прогноз не загрузится (причина будет видна в `/api/health`).
2. `.env` с ключом Яндекс.Карт (из `.env.example`). Если ключ ограничен по домену в кабинете
   разработчика Яндекса, добавьте туда адрес сервера, иначе карта не загрузится.

Открыть на сервере порты **8000** (дашборд) и **9201** (NDTP). Эмулятору организаторов в `targetHost`
указать адрес сервера; если эмулятор запущен на том же сервере в Docker — `host.docker.internal`
(с `--add-host=host.docker.internal:host-gateway`). Сборке нужен интернет (pip, npm, образы);
в работе стек занимает около 800 МБ памяти.

### Без Docker

Нужны Python 3.12+ и Node.js 20+. Все команды выполняются из корня проекта.

```bash
python -m pip install -r requirements.txt
npm --prefix web install && npm --prefix web run build   # дашборд -> web/dist, его отдает API
python -m uvicorn app.api:app                            # API + дашборд: http://localhost:8000
```

Режим «Симуляция» требует подготовленного дня, около 15 минут:

```bash
./run_all.sh
```

Файл сдачи (MAE на validate) воспроизводится одной командой, результат в `submissions/submission_v2_catboost_telemetry.csv`:

```bash
python scripts/model_v2.py
```

## Инструкция для жюри

### 1. Подать поток

Запустите систему (раздел [Запуск](#запуск)) и во втором терминале подайте телеметрию одним из двух способов.

**Исторический датасет через NDTP.** Скрипт берет треки из `data/hackathon/<часть>/traffic.csv` и шлет их в приемник обычными пакетами NDTP, с теми же `unit_id`, координатами и временем, что в выгрузке, ускоряя время:

```bash
python scripts/ndtp_replay.py --start 12:00 --minutes 90 --speed 40
```

Параметры: `--part validate|test`, `--start ЧЧ:ММ` (время суток данных), `--minutes`, `--speed` (ускорение), `--units` (ограничить число машин), `--port`, `--hide-ids`.

С `--hide-ids` номера терминалов подменяются, и сервис их не знает. Так проверяется map matching: система сама определяет рейс машины по ее треку и расписанию, после чего машина получает прогноз. В карточке такой машины написано «рейс определен по треку».

**Эмулятор организаторов** (нужен Docker):

```bash
docker load -i data/hackathon/ndtp-telemetry-emulator.tar
docker run --rm -p 18080:18080 --add-host=host.docker.internal:host-gateway --name ndtp-emu ndtp-telemetry-emulator:1.0
curl -X POST localhost:18080/api/config -H "Content-Type: application/json" -d "{\"targetHost\":\"host.docker.internal\",\"targetPort\":9201,\"units\":[{\"unitId\":1166336,\"intervalMs\":5000,\"autoGenerate\":true,\"cells\":[]}]}"
```

С `autoGenerate: true` эмулятор присылает случайные точки без маршрута: так проверяется прием и разбор пакетов, прогноза по такой машине нет. Подробнее — [docs/ndtp-emulator.md](docs/ndtp-emulator.md).

Проверить, что пакеты доходят: `GET http://localhost:8000/api/live/units` (счетчики `connections`, `fixes`, `crc_errors`).

### 2. Увидеть прогнозы и тревоги

Откройте http://localhost:8000 и переключитесь на **Live**:

- **Карта.** Машины окрашены по уровню риска: зеленый, желтый, красный. Серые — нет прогноза: машина без расписания или мало отметок.
- **Верхние KPI.** ТС на связи, высокий риск через 10–15 мин, уже опаздывают, не сопоставлено с расписанием.
- **Панель «Раннее предупреждение».** Машины с высоким риском, которые пока идут по графику: риск, остановка прогноза, плановое и ожидаемое время, причина.
- **Карточка ТС.** Клик по машине или тревоге: целевая остановка через 10–15 минут, ожидаемое отклонение, вероятность опоздания, причины.

Признаки считаются по последним 10 минутам потока, поэтому полная картина складывается после 10 минут потока. При `--speed 40` это примерно 15 секунд после старта проигрывателя.

Режим **Симуляция** воспроизводит записанный день с шкалой времени, медленными перегонами и проверкой сбывшихся тревог.

Те же данные через API: `GET /api/live/snapshot` (машины, KPI, тревоги, карточки), `GET /api/live/units` (сырые положения из NDTP), `GET /api/health` (готовность источников и моделей).

Метрики модели для сдачи воспроизводятся на данных хакатона:

## Производительность

Замеры на ноутбуке, CPU, один процесс Python:

| Что | Результат |
|---|---|
| Разбор пакетов NDTP | ~86 000 пакетов/с, ошибок CRC 0 |
| Прием отметок в буфер прогноза | ~690 000 отметок/с |
| Прогноз для одной машины (признаки, оценка отставания, регрессор, классификатор, SHAP-причины) | ~43 мс |
| `GET /api/live/snapshot` при потоке в реальном времени, ~20 машин | медиана 130 мс, p95 300 мс |
| Map matching незнакомых машин (входит в предыдущую строку) | медиана 0–25 мс, до 55 мс на запрос |
| Кадр записанного дня (`/api/replay/frame`) | медиана 2.5 мс, p95 3.9 мс |
| Загрузка моделей и расписания при старте | ~1.3 с |

Прогноз машины пересчитывается, только если от нее пришли новые отметки, и не чаще раза в 5 секунд. За один запрос пересчитывается не больше 8 машин, остальные отдаются из кэша, а сопоставление по треку пробуется не больше чем для 5 незнакомых машин. Поэтому время ответа дашборду ограничено сверху и не растет с числом машин в потоке.

## Дополнительные возможности

- **Причины прогноза.** SHAP-вклады признаков переводятся в фразы для диспетчера: «уже отстает от графика», «долгий простой за последние 10 мин», «при текущей скорости не успевает к остановке». Словарь фраз — `ml_service/reasons.py`, правится без программиста.
- **Вероятности классов.** Отдельный классификатор early / ontime / late дает вероятность опоздания, по ней считается уровень риска.
- **Отставание без подсказки.** В потоке NDTP нет `cur_dev_s`. `ml_service/cur_dev.py` оценивает его по отметкам и расписанию: находит проход остановки по траектории или прогнозирует прибытие по положению на маршруте. Модели для потока обучены на этой оценке.
- **Map matching.** Если терминала нет в таблице `unit_id` → `tr_id`, рейс определяется по треку: последние 10 минут отметок сравниваются с плановой ниткой каждого рейса (цепочка остановок и плановых времен). По одним остановкам ходят до шести машин, поэтому рейс различается по времени: у своего рейса отклонение от графика почти постоянно, у чужого рейса того же маршрута и у обратного направления оно плывет. Привязка — после двух совпадений подряд; рейс, у которого уже есть машина в потоке, не отдается другой. Точность на test — 99,6%, машины без расписания не привязались ни разу; в потоке validate за 90 минут верно привязана половина машин с расписанием, обычно за 2–5 минут, ошибочных привязок нет (`scripts/check_map_matching.py`).
- **Привязка отметок к маршруту.** Проекция положения машины на цепочку остановок ее рейса, расстояние до цели по маршруту, прохождение остановок по траектории.
- **Проигрыватель исторического датасета по NDTP** (`scripts/ndtp_replay.py`): подает реальные треки хакатона в приемник так же, как терминалы.
- **Устойчивость к обрывам.** Машина без свежих отметок получает статус «нет сигнала», а не последний прогноз. Машина без расписания видна на карте без прогноза. Без моделей или данных API работает и отвечает `503` с подсказкой. Сбой обработки одной отметки не рвет соединение с терминалом.
- **Записанный день** со шкалой времени, медленными перегонами и проверкой, сбылись ли прошлые тревоги.

## Качество моделей

Данные хакатона, метрика MAE в секундах, итоговая проверка на test:

| Модель | MAE на test, с |
|---|---|
| Прогноз «задержки нет» (0) | 103.34 |
| Baseline: прогноз = `cur_dev_s` | 93.36 |
| v1: CatBoost на 3 признаках | 76.94 |
| **v2: CatBoost на 24 признаках (файл сдачи)** | **66.16** |
| v2 для потока: `cur_dev_s` из нашей оценки | 73.82 |

Число деревьев подбирается по `GroupKFold(5)` по `tr_id` внутри train, финальная модель учится на train + test. Для точки `T` используется только телеметрия с `event_time <= T` и плановое расписание, фактическое время из расписания не используется.

Классификатор early / ontime / late на test: accuracy 0.771, F1 macro 0.673, log loss 0.562. Правило «класс по прогнозу регрессора»: 0.725, 0.586 и 0.628.

Оценка `cur_dev_s` без подсказки на test: есть для 90.9% точек, медианная ошибка 24 с.

## Как устроено

```
 терминалы / эмулятор / ndtp_replay
          │ NDTP по TCP :9201
          ▼
 app/service/ndtp_server ──► ml_service/live ──► признаки (features), cur_dev,
 (разбор пакетов)             (буфер отметок)     регрессор, классификатор, причины
          │                          │
          ▼                          ▼
     app/api.py (FastAPI) ◄──── прогнозы по машинам
          │ JSON
          ▼
     web/ — дашборд
```

Признаки для обучения и для потока считает один и тот же код, `ml_service/features.py`. Модель в работе видит ровно то, на чем училась.

| Каталог | Что лежит |
|---|---|
| `ml_service/` | `features.py` — признаки; `models.py` — обучение и `predict_class_probs`; `reasons.py` — причины; `cur_dev.py` — оценка отставания; `map_matching.py` — рейс по треку; `live.py` — прогноз по потоку; `server.py` — ML-модуль как HTTP-сервис |
| `app/` | `api.py` — маршруты; `service/` — приемник NDTP, live-срез, записанный день; `data_sources/` — разбор NDTP и расписания data.mos.ru; `config.py` — пороги и порты |
| `web/` | Дашборд: вся предметная логика на сервере, фронтенд только рисует готовый ответ API |
| `scripts/` | Обучение и проверки моделей, файл сдачи, проигрыватель NDTP |
| `models/` | Обученные модели |

Скрипты в `scripts/`:

| Скрипт | Что делает |
|---|---|
| `model_v2.py` | Модель для сдачи и файл `submission_v2_catboost_telemetry.csv` |
| `model_online.py` | Модели для потока (обучены на оценке `cur_dev_s`) |
| `model_classifier.py` | Классификатор early / ontime / late |
| `check_service.py` | Проверка оценки `cur_dev_s` |
| `check_map_matching.py` | Проверка map matching: угадывает ли рейс по треку при скрытой таблице терминалов |
| `show_reasons.py` | Примеры причин прогноза |
| `model_city.py` | Эксперимент: «обстановка в городе» вместо времени суток (хуже v2 на 3.8 с, не используется) |
| `ndtp_replay.py` | Подача исторического датасета по NDTP |
| `explore.py`, `model_v1.py` | Разведка данных и первая модель |

ML-ядро работает либо в процессе API, либо отдельным сервисом: `uvicorn ml_service.server:app --port 8100` (`POST /fixes`, `GET /forecasts`, `GET /health`), а backend запускается с `ML_URL=http://<адрес ML>:8100` и пересылает ему отметки пачками. Если ML-сервис недоступен, Live показывает машины без прогнозов, backend не падает.

Настройки через переменные окружения: `ML_URL` (пусто — ML в процессе API), `NDTP_PORT` (9201), `NDTP_HOST` (0.0.0.0), `NDTP_VERIFY_CRC` (1), `NDTP_PLAN_TZ_OFFSET_S` — сдвиг `gps_time` к шкале расписания (0).

## Ограничения

- **Номер маршрута.** В данных хакатона его нет, только `tr_id`. На дашборде в Live вместо номера маршрута показывается `tr_id`.
- **Прогноз по потоку — только для рейсов из данных хакатона (39 расписаний).** Машина получает прогноз, если ее терминал есть в таблице `unit_id` → `tr_id` или если ее трек совпал с одним из этих рейсов. Остальные машины видны на карте без прогноза.
- **Часовой пояс расписания относительно `gps_time`** в раздаче не указан. По умолчанию сдвиг 0, при необходимости задается `NDTP_PLAN_TZ_OFFSET_S`.
- **Выборки хакатона — один день.** Все машины test и validate есть в train, поэтому на других днях и машинах ожидаемая ошибка выше.
- **Не реализовано:** What-if анализ, ONNX / TensorRT, ансамбль с PyTorch, инференс на GPU.
